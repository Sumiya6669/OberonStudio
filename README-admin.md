# Oberon Core — рабочая панель внутри сайта

Что добавлено к сайту: раздел `/admin` (заявки, компании, конфигурации 1С,
учёт времени, очередь заданий и журнал), схема базы в Supabase и приём заявок
с формы прямо в базу.

Полное обоснование решений — в `september-plan.md` и `jarvis-core-spec.md`
рядом с этой папкой.

---

## Порядок запуска

### 1. Отдельный проект Supabase

Заведите **новый** проект, не тот, где живёт AI Searcher: там свои 50 таблиц,
184 миграции и 103 политики, мешать их незачем.

### 2. Миграции

Прогнать по порядку через SQL Editor или Supabase CLI:

```
supabase/migrations/
  001_core.sql        схемы, роли, клиенты, люди, реестры
  002_queue.sql       очередь заданий, захват, повторы, сборщик аренд
  003_rights.sql      права, подтверждения, накопление автономности
  004_log.sql         журнал действий (только дописывается)
  005_treasury.sql    квоты и расход по каждому клиенту отдельно
  006_crm.sql         компании, заявки, оценки, время, документы
  007_dev.sql         конфигурации 1С и отчёты агентов
  008_rls.sql         политики RLS генератором: забыть таблицу невозможно
  009_seed.sql        реестры и ваш клиент (tenant «oberon»)
  010_public_api.sql  приём заявки с формы: функция public.submit_lead
  011_views.sql       витрины схемы app для экранов
```

Порядок обязателен: 008 создаёт политики по факту существования таблиц,
011 пересоздаёт представления целиком (drop view сносит зависимые каскадом).

### 3. Пользователь

Supabase → Authentication → Users → Add user: ваша почта и пароль.
При первом входе в `/admin` панель сама вызовет `core.link_me` и заведёт
человека в системе с ролью владельца.

### 4. Переменные окружения

Vercel → Settings → Environment Variables. Образец — в `.env.example`.

| Переменная | Где нужна | Что это |
|---|---|---|
| `VITE_SUPABASE_URL` | браузер | адрес проекта |
| `VITE_SUPABASE_ANON_KEY` | браузер | публичный ключ |
| `SUPABASE_URL` | `/api/lead` | тот же адрес |
| `SUPABASE_ANON_KEY` | `/api/lead` | тот же публичный ключ |
| `TELEGRAM_BOT_TOKEN` | `/api/lead` | токен бота |
| `TELEGRAM_CHAT_ID` | `/api/lead` | куда слать заявки |

**Ключ `service_role` не нужен нигде.** Форма пишет в базу через функцию
`public.submit_lead` с ограниченными правами, а строки в панели отсекает RLS
по вошедшему пользователю. Публичный ключ на то и публичный: он не даёт
доступа к чужим данным.

### 5. Проверка

```bash
npm install
npm run dev     # http://localhost:5173/admin
npm run build   # должен пройти без ошибок
npm run lint
```

Без переменных Supabase публичная часть сайта работает как раньше,
а `/admin` честно сообщает, что не настроен.

## Решения, которые стоит понимать, прежде чем менять

**Порядок в `/api/lead`: сначала база, потом Telegram.** Telegram — канал
доставки, а не хранилище. Если бот недоступен или упёрся в суточный предел,
заявка всё равно в системе, и клиенту не за что извиняться. Обратный порядок
означает потерянные обращения, о которых никто не узнает.

**Правила живут в базе, а не в интерфейсе.** Опознание клиента по домену
почты — функция `crm.resolve_company`. Защита от двойного нажатия кнопки —
уникальный индекс `job_dedupe_idx`. Запрет принять оценку без человека —
триггер. Всё это нельзя обойти ни вторым каналом загрузки, ни ручной вставкой,
ни новым экраном.

**Страж маршрута `/admin` — удобство, а не защита.** Настоящая защита — RLS:
без сессии не вернётся ни одной строки, а попытка записать строку чужому
клиенту даёт исключение на уровне базы.

**Домены и телефоны компании — рабочие данные, а не справка.** По ним
Регистратор опознаёт клиента во входящем письме. Пустой список доменов
означает, что заявки этого клиента придут «ничьими».

**Задания агентам разработки не имеют обещания по времени.** Раннер живёт на
вашей машине и поднимается вместе с рабочим днём: задания копятся в очереди и
разбираются пачкой. Обещание в минуту даётся только на приём заявки — это
облако, оно работает всегда.

# Четыре раздела панели

Панель разделена на СРМ, Бух учет, ИИ и Администрирование. Прежние экраны
переехали под СРМ; прежний адрес `/admin/queue` переадресуется на
`/admin/ai/queue`, чтобы старые закладки не выглядели сломанной панелью.

## Что нужно сделать один раз

**1. Применить миграции 014, 015, 016** в SQL-редакторе Supabase, по порядку.
Каждая применяется целиком, одним запуском.

| файл | что добавляет |
|---|---|
| `014_acc.sql` | схема `acc`: план счетов, документы, проводки, витрины прибыли и денег |
| `015_cms.sql` | схема `cms`: страницы, блоки, справочники, история правок, `public.site_content()` |
| `016_watch.sql` | витрины наблюдения, `public.ai_pulse()`, обёртки `public.acc_*` |

**2. Открыть новые схемы для API.** Supabase → Settings → **Data API** →
Exposed schemas. Должно быть перечислено:

```
public, core, crm, dev, app, acc, cms
```

Без `acc` и `cms` разделы «Бух учет» и «Сайт» будут отвечать
`Invalid schema` — ровно так же, как это было с `crm` и `app`.

**3. Проверить, что панель собралась**: `npm run build`.

## Бух учет

Управленческий учёт, не налоговый. Ни форм 100/200/300, ни ЭСФ здесь нет и не
планируется — это работа для 1С. Панель отвечает на четыре вопроса: сколько
денег, кто сколько должен, сколько стоит час, зарабатываю я или проедаю.

Двойная запись внутри есть, и без неё «прибыль» была бы мнением. Правила
живут в базе, а не в интерфейсе:

* **дебет обязан равняться кредиту** — иначе документ не проводится;
* **проводок минимум две**, и ни одна не ложится на группу счетов;
* **проведённый документ неизменяем** — ни правкой, ни удалением. Ошибка
  исправляется сторнирующим документом с собственной датой и причиной;
* **проводит только вошедший человек** — агент документы не проводит;
* **счёт из часов собирает база** (`acc.invoice_from_time`), а не браузер:
  защита от повторного выставления — это колонка `invoiced_in` и триггер.
  Два открытых окна панели не смогут выставить один час дважды;
* **счёт на ноль не выставляется**, и «за период нет невыставленных часов» —
  это отказ, а не пустой документ.

Счета и оплаты создают **черновики** проводок автоматически. Черновик не
участвует ни в прибыли, ни в сальдо, пока его не провели: цифры в отчётах
складываются только из проведённого.

Себестоимость часа считается грубо — все расходы месяца на оплачиваемые часы
месяца. Подписки и связь честно по клиентам не делятся, и попытка разложить
их точнее дала бы красивую выдуманную цифру. Грубой правды достаточно, чтобы
увидеть, ниже какой ставки работать нельзя.

## ИИ

Живой экран опрашивает базу раз в три секунды **одним** вызовом
`public.ai_pulse()`. Шесть отдельных запросов в такт дали бы шесть разных
мнений о том, который час: доска показывала бы одно состояние, лента другое.

Экран обязан говорить, насколько он живой, поэтому сверху всегда написано,
когда данные обновлялись. Вкладка ушла в фон — опрос останавливается. Связь
потеряна — прежние данные остаются, но с честной подписью «связь потеряна,
данные от такого-то времени».

Про запас в 15 секунд у ленты шагов: строка журнала получает время НАЧАЛА
своей транзакции, а видимой становится при её фиксации — позже. При честном
условии «строго новее последней метки» шаг, попавший в этот зазор, не
показался бы **никогда**. Поэтому лента берёт с перекрытием, а повторы
отбрасываются по `id` в браузере: повтор дёшев, потерянный шаг — нет.

Матрица прав строится от полного набора «агент × действие», а не от выданных
прав: отсутствие записи означает запрет, и его надо видеть, а не угадывать.
Рядом с каждым запретом видно, сколько подтверждений без правок агент собрал
подряд и сколько осталось до порога самостоятельности.

## Администрирование

**Люди и доступ.** Два разных списка. «Допущенные адреса» — кто вообще может
войти; при первом входе база сверяет подтверждённый адрес из `auth.users`
с этим списком. «Люди» — те, кто уже вошёл, и те, кому пишет Вестник; отдельно
видно, нажал ли человек «Старт» у бота, потому что «есть chat_id» и «нам
разрешено писать» — разные факты.

**Реестры агентов.** Здесь живут два предела, из-за которых чаще всего
«всё стоит, а непонятно почему»: `max_parallel` (сколько заданий агент берёт
одновременно) и `lease_sec` (сколько держит). Слишком маленький срок аренды
для длинной работы означает, что задание будут отбирать у работающего агента.

**Состояние системы.** Разделы журнала на месяцы вперёд, таблицы без RLS,
брошенные аренды, молчащий раннер. Всё это ломается тихо, и заметить это
можно только глядя специально.

## Сайт

Содержимое правится из панели. Главное свойство: **пока в базе ничего не
опубликовано, сайт показывает то же, что и раньше** — тексты из кода.
Публикация начинает перекрывать код; черновики не влияют ни на что; ошибка
сети при чтении содержимого тоже безвредна, потому что «нет данных» и «как
было» здесь одно и то же. Сайт не может сломаться из-за CMS.

Справочники (услуги, кейсы, отзывы, вопросы, стек, решения) — одна таблица
`cms.item` с описанием полей в `cms.collection`. Интерфейс рисуется по этому
описанию, поэтому новый справочник или новое поле — это вставка строки, а не
новый экран и не миграция.

Публиковать пустое нельзя: обязательные поля перечислены в описании
справочника, и база отказывает с перечислением того, чего не хватает.
Пустая карточка — это то, что видит клиент.

Языки лежат в одном `jsonb`. Непереведённое поле сайт отдаёт по-русски, и
делает это **база** (`cms.loc`), а не браузер: правило про язык одно, и
повторять его в каждом компоненте — значит однажды забыть. Перевод из одних
пробелов переводом не считается.

Правки пишут историю (`cms.revision`). Переписать или удалить историю нельзя
даже из панели: права отозваны в базе. CMS без истории — это способ однажды
потерять абзац и не узнать, каким он был.

Анонимный посетитель не имеет доступа ни к одной таблице `cms`: он получает
только опубликованное и только через функцию `public.site_content()`.

## Маршрутизация после предрендера

В `dist` теперь лежат три разных вида файлов, и путать их нельзя:

| файл | что это |
|---|---|
| `index.html`, `services/index.html`, … | **собранные страницы сайта** с текстом и мета-тегами |
| `app.html` и `admin/index.html` | **пустая оболочка**: `<div id="root"></div>` и ничего больше |
| `robots.txt`, `sitemap.xml`, `llms.txt` | служебные файлы |

Порядок у Vercel такой: переадресации → **поиск файла на диске** → правила
переписывания адреса (`rewrites`). Поэтому собранные страницы всегда
выигрывают у общего правила: для `/services` файл находится раньше.

Вход в панель сделан файлом, а не правилом. `dist/admin/index.html` — та же
пустая оболочка, и `/admin` открывается на этапе поиска файла, до всяких
правил. Это сознательная страховка: маршрутизация — самое хрупкое место
деплоя, а дверь в панель ломаться не должна. Вложенные адреса
(`/admin/money`, `/admin/tickets/42`) файлами быть не могут и приходят через
общее правило «всё остальное → `app.html`».

Оболочка, а не `index.html`, как было раньше: `index.html` теперь не
оболочка, а **собранная главная страница**. Отдать её на `/admin` значит
попросить браузер подхватить разметку главной на маршруте панели — это
расхождение гидратации, мелькнувшая главная и ошибки в консоли.

### Почему из конфигурации убран `cleanUrls`

Он выглядел безобидно — «убрать `.html` из адресов» — и сломал панель.
При `cleanUrls: true` файл `app.html` перестаёт быть доступен по адресу
`/app.html`: он доступен только по `/app`, а с `/app.html` стоит
переадресация. Правило `«/admin → /app.html»` при этом указывает на адрес,
которого больше нет, — и Vercel отвечает 404. Причём молча: конфигурация
валидна, деплой зелёный, заголовки из того же файла работают.

Признак именно этой поломки: 404 отдают **все** несуществующие адреса
(`/zzz`, `/adminx`), а собранные страницы открываются. Значит правила
переписывания не срабатывают вовсе, а файлы находятся.

Стоимость отказа от `cleanUrls`: адреса `/index.html` и `/services/index.html`
перестали переадресовываться на короткие. Дублирование закрыто тегом
`<link rel="canonical">`, он на каждой странице.

В `vercel.json` нельзя писать комментарии и посторонние ключи: Vercel
проверяет файл по схеме и на неизвестном ключе роняет весь деплой.

Локальная проверка: `npm run dev` работает как обычно, панель открывается.
А вот `npm run preview` про `vercel.json` не знает и на `/admin` ответит 404 —
это особенность предпросмотра, а не поломка.

## Языковые адреса

`/services` — русская версия, `/kz/services` — казахская, `/en/services` —
английская. Русская остаётся корнем сайта и `x-default`.

Правило без исключений: **адрес определяет язык**. Не запомненный выбор и не
язык браузера. Иначе один и тот же адрес показывал бы разным людям разный
текст, и `hreflang`, кэш и предрендер начали бы врать одновременно.
Переключатель языка не меняет состояние, а переходит на другой адрес.

Все внутренние ссылки публичного сайта идут через `LocaleLink` — обёртку,
которая дописывает текущую приставку. Обычная ссылка `/services` со страницы
`/kz/faq` молча вернула бы человека на русскую версию, и казахский сайт
оказался бы тупиком из одной страницы.

Собирается 27 страниц (9 × 3 языка) плюс разборы по 1С.

## Разборы по 1С — `/1c`

Отдельные страницы под запросы, с которыми человек приходит в поиск своими
словами: «не проводится документ 1С», «не грузится выписка из банка».
Раздел «Услуги» на такие запросы не отвечает — он отвечает на запрос того,
кто уже решил искать подрядчика, а таких в разы меньше.

Содержимое — справочник `answer` в CMS (Сайт → Справочники → Ответы по 1С).
Добавили разбор в панели → он появится на сайте следующей сборкой сам:
адреса берутся из опубликованного, а не из списка в коде.

Только по-русски и намеренно: казахская и английская версии, собранные ради
симметрии, были бы страницами без читателей. Поэтому у них нет `hreflang` —
указать перевод, которого нет, хуже, чем не указывать ничего.

Порядок блоков повторяет порядок разговора: короткий ответ → как это
выглядит → отчего бывает → что проверить самому → и только в конце, с
условием, когда нужен программист. Страница, которая начинается с «оставьте
заявку», закрывается раньше, чем прочитывается.

## Публикация доходит до сайта

Страницы собираются заранее, поэтому правка в панели попадает на сайт только
со сборкой. Раньше это было тихим разрывом: панель писала «опубликовано»,
сайт показывал старый текст.

Теперь на всех трёх экранах раздела «Сайт» висит полоска состояния. Пока
есть правки, до сайта не доехавшие, она предупреждает и предлагает кнопку
«Обновить сайт».

Как это устроено:

| часть | где живёт | за что отвечает |
|---|---|---|
| адрес пересборки | переменная `DEPLOY_HOOK_URL` в Vercel | секрет, в браузер не попадает |
| `/api/rebuild` | функция сайта | доставка: спросить базу и дёрнуть адрес |
| `public.rebuild_take()` | база | кому можно и как часто (6 раз в час) |
| `cms.rebuild` | база | след: кто, когда, зачем, чем кончилось |
| `app.v_site_freshness` | база | отстал ли собранный сайт от опубликованного |

Пересборку просит человек — агент этого делать не может. Отказ по частоте
возвращается как обычный ответ с причиной, а не как ошибка.

## Что нужно сделать руками в поиске и картах

Это единственное, чего нельзя сделать из кода: везде нужен вход под вашей
учётной записью.

1. **Google Search Console** → добавить ресурс `oberon-studio.vercel.app`,
   выбрать подтверждение мета-тегом, скопировать код.
2. **Яндекс.Вебмастер** → то же самое, там свой код.
3. Оба кода вставить в панели: **Сайт → Настройки** → «код подтверждения».
   Нажать «Обновить сайт». Через минуту вернуться и нажать «Подтвердить».
4. В обоих сервисах добавить карту сайта: `/sitemap.xml`.
5. **2ГИС** и **Google Business** → завести карточку организации.
   Полученные ссылки вписать в настройках — они попадут в разметку
   `sameAs`, и поиск свяжет сайт с точкой на карте.

Пока карточек нет, в разметке нет ни адреса, ни рейтинга: выдумывать их
нельзя — это заявление, за которое отвечает владелец сайта, а не код.

## Абонементы и обязательства по срокам

Два самых денежных способа продавать услуги 1С не описываются часами:
«сопровождение» — клиент платит каждый месяц и получает пакет часов;
«скорая» — клиент платит за обращение, но покупает СРОК реакции. В обоих
случаях предмет сделки — обещание, а не работа.

| сущность | что это |
|---|---|
| `crm.plan` | тариф, то есть прайс на сегодня |
| `crm.subscription` | проданный абонемент с условиями **на момент продажи** |
| `crm.ticket.react_by` / `resolve_by` | обещанные сроки, считаются при приёме |
| `crm.ticket.first_reply_at` | когда ответили в первый раз |
| `app.v_sla_breach` | что уже просрочено |
| `app.v_sla_month` | держим ли обещание в среднем |

Условия **копируются** в абонемент, а не берутся из тарифа по ссылке.
Поменяли прайс — у старого клиента ничего не изменилось. Иначе правка цены
задним числом молча переписывала бы уже проданное.

Первый ответ фиксируется **сообщением** от нас, а не сменой статуса: клиент
видит ответ, а не то, что кто-то переключил статус.

Один действующий абонемент на клиента — это уникальный индекс, а не
договорённость. Два действующих означали бы спор о том, из какого пакета
списывать часы.

Счёт за период = цена абонемента плюс перерасход по ставке. Часы, попавшие
в счёт, помечаются, поэтому второй раз их не выставить.

## Ставка и безубыточность

Минимальная ставка = расходы месяца / **проданные** часы. Не отработанные:
переписка, продажи, счета и собственная система тоже занимают время, но их
никто не оплачивает. Поэтому цифра всегда выше, чем кажется.

Витрины `app.v_rate_health` (по месяцам) и `app.v_rate_baseline` (средние за
три закрытых месяца) отдают только факты. Прикидка «какая ставка нужна»
считается в панели: это черновик решения, а не факт, и в базе ему не место.

Текущий месяц в основу не входит — он не закрыт и всегда выглядит убыточным.

## Офферы — `/uslugi`

Страницы под конкретную покупку: что входит, **что не входит**, как проходит,
сроки, стоимость. Справочник `offer` в CMS, адреса берутся из
опубликованного, только по-русски.

Раздел «что не входит» стоит сразу после «что входит», а не мелким шрифтом
в конце: возражение, снятое до разговора, экономит время обеим сторонам.

Цена может быть пустой — это показывается как «Цена по запросу». В разметку
JSON-LD пустая цена не попадает: ноль в выдаче прочитается как «бесплатно».

## Расписка за заявку

После отправки формы человек видит номер обращения (`OS-00005`) и время, до
которого обещан ответ. Время берётся из `crm.ticket.react_by` — того же поля,
по которому панель считает просрочку. Поэтому сайт и панель не могут
разойтись: поменяли срок в тарифе, и форма начала обещать новое.

Повторное нажатие кнопки отдаёт **тот же** номер, а не новую заявку: с точки
зрения человека это одно обращение, а новый номер означал бы, что первый
потерян.

## Найденная дыра: разделы журнала читались напрямую

Журнал `core.action_log` и учёт расхода `core.usage_event` разбиты на разделы
по месяцам. RLS был включён на родительской таблице, и через неё всё работало
правильно. Но PostgreSQL **не применяет политики родителя к обращению прямо
в раздел**, а раздел — обычная таблица в открытой схеме `core`.

На чистой базе с двумя клиентами:

```
select count(*) from core.action_log           → 1   (правильно)
select count(*) from core.action_log_2026m09   → 2   (чужая запись)
```

Пока клиент один, это ничего не значит. Со вторым это утечка журнала
действий между клиентами. Панель при этом показывала «ни одной таблицы без
разграничения доступа», потому что её проверка исключала разделы.

Закрыто миграцией 026 тремя способами сразу: RLS и политика на каждом
разделе, отзыв прямых прав (приложение обращается только к родителю), и то
же самое в функциях создания разделов — иначе через год появился бы новый
открытый раздел. Проверка в панели теперь считает разделы.
